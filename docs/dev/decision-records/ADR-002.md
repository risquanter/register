# ADR-002: Logging Strategy

**Status:** Accepted  
**Date:** 2026-01-12  
**Tags:** logging, telemetry, observability, zio

---

## Context

- OpenTelemetry already provides **request tracing** (spans) and **business metrics**
- ZIO's built-in logging outputs structured logs to console in a structured format suitable for export
- Third-party libraries route their logs through SLF4J/Logback by default, producing a different format and format from ZIO logs — unified correlation requires an explicit bridge
- Unstructured stderr writes (e.g., `System.err.println`) bypass log level filtering, structured formatting, and telemetry correlation
- Logback's behaviour without an explicit configuration file is undefined and environment-dependent; a managed `logback.xml` is required for predictable output

---

## Decision

### 1. Telemetry for Tracing and Metrics, Logging for Diagnostics

OpenTelemetry handles **what happened** (spans, metrics). Logging handles **why it failed** (errors, debug).

| Use Case | Tool |
|----------|------|
| Request flow tracing | OpenTelemetry Spans |
| Business metrics (counters, histograms) | OpenTelemetry Metrics |
| Error diagnostics with stack traces | `ZIO.logError` |
| Development debugging | `ZIO.logDebug` |
| Audit trail | `ZIO.logInfo` |

```scala
// GOOD: Use telemetry for tracing
tracing.span("computeLEC") {
  // Use logging for errors
  effect.tapError(e => ZIO.logErrorCause("Simulation failed", Cause.fail(e)))
}
```

### 2. Defer SLF4J Bridge Integration

**Rationale:** This codebase has minimal third-party libraries that produce meaningful logs:
- OpenTelemetry SDK (internal diagnostics only)
- Netty via ZIO HTTP (connection errors)
- metalog-distribution (silent)

The SLF4J bridge (`zio-logging-slf4j2-bridge`) would unify log formats and enable trace correlation in third-party logs, but adds complexity for marginal benefit given our limited external log sources.

**Decision:** Do not add the bridge now. Revisit if:
- Adding database driver (e.g., Quill/Postgres) with verbose logging
- Adding HTTP client libraries with request logging
- Trace correlation in third-party logs becomes a debugging requirement

```scala
// CURRENT: Third-party logs go through Logback (different format)
// ACCEPTABLE: Few third-party log sources in this codebase
// FUTURE: Add zio-logging-slf4j2-bridge if third-party logging increases
```

### 3. Configure Log Levels via logback.xml

Add explicit log level configuration for environment-appropriate verbosity:

```xml
<!-- modules/server/src/main/resources/logback.xml -->
<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{ISO8601} %-5level [%thread] %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>
  
  <!-- Application: DEBUG in dev, INFO in prod (via env override) -->
  <logger name="com.risquanter" level="${LOG_LEVEL:-INFO}"/>
  
  <!-- Quiet third-party noise -->
  <logger name="io.netty" level="WARN"/>
  <logger name="io.opentelemetry" level="WARN"/>
  
  <root level="INFO">
    <appender-ref ref="STDOUT"/>
  </root>
</configuration>
```

### 4. Replace Debug Hacks with Proper Logging

Remove `System.err.println` and use ZIO logging with Cause for stack traces:

```scala
// BAD: Debug hack
System.err.println(s"[ERROR] Simulation failed:")
error.printStackTrace(System.err)

// GOOD: Proper logging with cause
ZIO.logErrorCause(s"Simulation failed for $simulationId", Cause.fail(error))
```

### 5. Use Typed Error Hierarchy for Domain Errors

**Rationale:** String matching on error messages is fragile. ZIO's type system enables expressing error boundaries cleanly through a sealed trait hierarchy.

**Decision:** Every failure is a value of `Failure`, whose shape ADR-010 §1
states. Each failure:
- Carries the zone its failing value came from, from which its log level is derived
- Carries its diagnostics as a typed list, rendered into the log line and never onto the wire
- Propagates type-safely to the HTTP boundary
- Is pattern-matched without string inspection

```scala
// LOG LINE: derived from the failure, never from the wire case
f.logMessage      // "Rejected: [request.Name] A value is required"
f.logAnnotations  // every Diagnostic rendered under its declared key, plus trust_zone
f.origin          // Caller for the Client zone, Service for every other zone

// SERVICE LAYER: refuse with the zone the content came from
ZIO.fromEither(IrminCommit.refine(raw).left.map(refusals =>
  Failure.rejected(TrustZone.Peer(PeerZone.Store), refusals, List(Diagnostic.RawValue(raw.hash)))))

// HTTP BOUNDARY: pure projection, no string inspection (ADR-010 §5)
failure.toWire(trace, scope)
```

The `AppError` sealed trait still holds the leaves that have not moved onto this
shape, and carries an abstract `origin` of its own under the same rule.

**Benefits:**
- Compiler-checked exhaustiveness for error handling
- No fragile string matching
- One log level rule for every failure, read off its zone
- HTTP boundary remains pure
- A new zone or variant is a compile error until every derived function handles it

## Code Smells

### ❌ Using System.err for Error Logging

```scala
// BAD: Bypasses logging infrastructure
catch { case e: Exception =>
  System.err.println(s"[ERROR] $e")
  e.printStackTrace()
}

// GOOD: Uses ZIO logging with full cause
.tapError(e => ZIO.logErrorCause("Operation failed", Cause.fail(e)))
```

### ❌ Logging Instead of Telemetry for Request Tracing

```scala
// BAD: Using logs for tracing
ZIO.logInfo(s"Starting computeLEC for id=$id")
// ... operation
ZIO.logInfo(s"Completed computeLEC in ${duration}ms")

// GOOD: Using spans for tracing
tracing.span("computeLEC", SpanKind.INTERNAL) {
  tracing.setAttribute("risk_tree.id", id) *> operation
}
```

### ❌ Missing Log Level Differentiation

```scala
// BAD: Everything at INFO
ZIO.logInfo(s"Processing request")
ZIO.logInfo(s"Cache hit for key=$key")
ZIO.logInfo(s"Validation failed: $errors")

// GOOD: Appropriate levels
ZIO.logDebug(s"Processing request")      // Development only
ZIO.logDebug(s"Cache hit for key=$key")  // Performance debugging
ZIO.logInfo(s"Validation failed: $errors")     // Caller-caused: ordinary traffic
ZIO.logWarning(s"Irmin unavailable: $reason")  // Service-caused: operational signal
```

**A failure that becomes a response takes its level from who caused it.** A
caller-caused failure is `INFO`: the caller sent something the service correctly
refused, so the line records what happened and nothing here is wrong. A
service-caused failure is `WARNING` or above: a dependency failed, or there is a
defect. `INFO` rather than `DEBUG` for the caller case, because the deployment's
level defaults to `INFO` and at `DEBUG` those lines would be absent from a
default deployment.

The attribution is `Failure.origin`, derived from the failure's zone: `Caller`
for the `Client` zone and `Service` for every other zone. The match over the
zone has no wildcard, so a new zone cannot compile until it says which it is.

It is read from the internal failure and never from the wire case, because the
wire is deliberately coarser. Several internal failures share one wire case, and
they do not share an attribution. `WireError.AccessDenied` carries both an
`AccessDenied` at the `Client` zone, which is a caller's, and one at
`Peer(Authorization)`, where the authorization service refused. Taking the level
from the wire case would give one level to both, carrying that flattening into
the log, where the two must stay distinguishable.

## Implementation

| Location | Change |
|----------|--------|
| `Failure.scala` | `origin`, `logMessage` and `logAnnotations`, derived from the failure |
| `Diagnostic.scala` | The typed diagnostics and their declared log keys |
| `WireError.scala` | Typed projection onto the wire (no string inspection) |
| `CachedResultResolverLive.scala` | Log errors, wrap in `SimulationFailure` |
| `logback.xml` | Log level configuration |
